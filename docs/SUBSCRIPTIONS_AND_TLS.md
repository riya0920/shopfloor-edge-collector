# A driver contract that models subscriptions, and mutual TLS

The last two items on this project's not-built list. Generated by `run_pass4.py` in 5 s.

## 1. Telling "no change" from "no answer"

The OPC-UA leg found the problem in pass 3 and the README stated the diagnosis correctly: *a collector that reads "no data" as "device down" will declare a healthy machine dead the moment its temperature stops moving — which on an idle machine is most of the weekend.* The fix is not a bigger poll. It is a contract where one fetch answers two questions that a poll could only answer together:

| | |
|---|---|
| **what the device said** | zero or more readings, each with its own quality |
| **whether the device is there** | liveness, from *contact* — never from whether a value moved |

A polled device answers both at once, because a poll that returns data proves contact. A subscribed device does not, and that is the whole difference. So the subscription carries a **keep-alive**: the publisher promises to send something every interval, an empty publish if it has no news, and silence past the deadline is the only evidence of death either transport can offer.


### The original finding, now measured under both contracts

One initial publish, then 4 writes of which one repeats the previous value:

| write | device published? | readings | liveness | old contract | new contract |
|---:|:--:|---:|---|---|---|
| 61.0 | yes | 1 | FRESH | UP | UP |
| 62.0 | yes | 1 | FRESH | UP | UP |
| 62.0 | **no** | 0 | KEEPALIVE | **DOWN** | UP |
| 63.0 | yes | 1 | FRESH | UP | UP |

4 writes produced 3 notifications, because OPC-UA publishes on *change* and one write changed nothing. On that tick the old contract calls a working device dead, and the new one reports `KEEPALIVE` — the device answered, on time, with nothing to say.


### And on an idle machine, which is the case that matters

A device that is healthy and simply has no news, sampled 44 times over 2.5 s:

- old contract: **43 of 44 ticks call it DOWN** (98%)
- new contract: **0**, with 4 keep-alives seen

Then the device really dies. The new contract notices in **1.58 s** against its own deadline of 2.0 s — 0.5 s keep-alive × (3 missed allowed + 1). The deadline is deliberately not the interval: setting them equal declares a device dead on the first late packet, which is the original bug wearing a new name.

**Liveness is three-valued because the useful state is the middle one.** Collapsing `KEEPALIVE` into `FRESH` throws away how old the newest value is; collapsing it into `SILENT` is the bug. And `PolledAdapter` — which wraps every existing driver unchanged — never reports `KEEPALIVE`, because a polled transport provides no liveness signal and manufacturing one would be the same lie in the other direction.


## 2. Mutual TLS

Loopback is not a boundary; it is the absence of one that happens to be hard to reach. Ordinary TLS answers *is this the server I meant to talk to*. On a plant network the question that matters more is the other one: *is this gateway one of ours* — and a collector that verifies the uplink and then sends to it has protected the data in flight and authenticated nobody.


One CA, one server certificate, three client certificates and a rogue CA, all minted in-process per run. TLS TLSv1.3, TLS_AES_256_GCM_SHA384, with 1.2 and below refused rather than deprecated.


| case | expected | result |
|---|---|---|
| valid gateway, correct hostname | accept | accepted |
| no client certificate | refuse | refused — `Transport` |
| client signed by a different CA | refuse | refused — `SSL` |
| expired client certificate | refuse | refused — `SSL` |
| wrong server hostname | refuse | refused — `CertificateVerification` |
| client does not trust our CA | refuse | refused — `CertificateVerification` |

The accepted connection is identified as **`gateway-01`** — from the certificate, not from the payload. A gateway id in the message body is a claim; a gateway id in the peer certificate is established before the first byte of body is read.


### Why the refusals are the result and the acceptance is not

Showing that a valid client connects proves almost nothing, because a server with verification switched off passes that test too. The control runs the same clients against a `CERT_NONE` server:

- accepts a client with **no certificate**: `True`
- accepts a client signed by a **different CA**: `True`
- peer common names seen: `[None, None]`

Both connections succeed and neither has an identity. That is what a happy-path TLS test cannot distinguish from the real thing.


### What this still is not

No CA infrastructure: no revocation, no OCSP, no renewal, no HSM, and the CA private key lives in the same process as everything it signs. IEC 62443 SL-2 wants a managed identity lifecycle, and this demonstrates that the transport can carry and enforce identities — not that anybody is managing them. `docs/SECURITY_62443.md` §5 is updated rather than retired. Certificates are generated per run and never written to the repository, which a test asserts: a repository with a private key in its history has one forever.
